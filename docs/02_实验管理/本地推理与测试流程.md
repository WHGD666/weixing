# 本地推理与测试流程

## 文档目的

本流程用于验证第一版 `best.pt` 是否可以稳定加载、正确输出 25 类检测结果，并逐步对齐比赛方 Docker 评测接口。当前只做本地验证，不构建 Docker 镜像，不提交官方评测。

## 当前测试入口

代码位置：

- `shiyan/src/inference/`：推理、切片、后处理、结果格式校验。
- `shiyan/scripts/test_inference.py`：固定验证清单抽样测试。
- `shiyan/scripts/run_inference.py`：目录输入的统一推理入口。
- `shiyan/scripts/evaluate_official.py`：按 Metric Contract v0 计算内部指标。
- `shiyan/tests/test_inference_contract.py`：不依赖模型的格式和后处理单元测试。

所有命令都从仓库根目录执行。模型路径、数据路径和输出路径必须通过参数传入，代码不能写死 Windows 盘符。

## 第一阶段：抽样冒烟测试

执行：

```powershell
python shiyan/scripts/test_inference.py `
  --model runs/detect/runs/train/exp001_original_yolo11s_baseline/weights/best.pt `
  --image-list shiyan/data_registry/split_assignments/v1_scene_80_20/val.txt `
  --output-dir runs/test/exp001_baseline_sample `
  --sample-count 12 `
  --mode direct `
  --save-vis
```

必须检查：

1. 程序正常结束，没有模型加载、CUDA 或类别顺序错误。
2. `result.json` 存在，且 12 张图片全部有结果。
3. `timings.json` 存在，记录每张图片的尺寸、耗时和检测框数量。
4. 可视化图片中的框落在图像范围内，类别名称没有明显错位。
5. 输出框是原图像素坐标，不是 YOLO 归一化坐标。

## 第二阶段：内部指标核验

执行：

```powershell
python shiyan/scripts/evaluate_official.py `
  --predictions runs/test/exp001_baseline_sample/result.json `
  --image-list runs/test/exp001_baseline_sample/image_list.txt `
  --timings runs/test/exp001_baseline_sample/timings.json `
  --output-dir runs/test/exp001_baseline_sample/metrics
```

评估规则：

- 预测按 score 从高到低处理。
- 同一预测只能匹配一个真实框，同一真实框只能被匹配一次。
- 类别 ID 必须一致，重复预测计为 FP。
- FSC（类别 24）使用 IoU 0.35。
- 舰船和飞机使用 IoU 0.50。
- 输出 25 类、舰船、飞机、发射车和整体的 TP、FP、FN、Recall、FDR。

抽样集只有 12 张图，不用于判断比赛的整体性能。它的作用是尽快发现坐标、类别、输出格式和评估实现错误。

## 全量错误分析

全量指标完成后，执行：

```powershell
python shiyan/scripts/analyze_errors.py `
  --predictions runs/test/exp001_baseline_val_direct_20260829/result.json `
  --image-list runs/test/exp001_baseline_val_direct_20260829/image_list.txt `
  --output-dir runs/test/exp001_baseline_val_direct_20260829/error_analysis `
  --top-images 30
```

错误分析沿用同一套类别匹配和 IoU 阈值，不另造一套评分规则。它会定位每张图片的误检和漏检，并渲染代表性问题图：绿色表示匹配预测，橙色表示误检，红色表示漏检真实框。

## 类别相关阈值测试

如果全局阈值在不同大类之间产生明显冲突，可以从 `conf=0.25、iou=0.60` 的原始预测中只过滤指定类别。例如只把 FSC（类别 24）提高到 0.35：

```powershell
python shiyan/scripts/filter_class_thresholds.py `
  --input runs/test/exp001_baseline_val_direct_nms060_20260829/result.json `
  --image-list runs/test/exp001_baseline_val_direct_nms060_20260829/image_list.txt `
  --timings runs/test/exp001_baseline_val_direct_nms060_20260829/timings.json `
  --output-dir runs/test/exp001_baseline_class_fsc035_nms060_20260829 `
  --class-threshold 24=0.35
```

过滤后必须重新运行 `evaluate_official.py`。指定类别的阈值变化属于新的后处理实验，需要单独登记结果。

## COCO 结果导出

Docker 评测入口使用官方 `result.json`，框格式为原图像素坐标 `[x1,y1,x2,y2]`。作品测试结果另需标准 COCO 检测列表时，统一执行：

```powershell
python shiyan/scripts/export_coco.py `
  --input runs/test/exp001_baseline_sample/result.json `
  --output runs/test/exp001_baseline_sample/coco_results.json
```

导出文件中的框格式为 COCO 规定的 `[x,y,width,height]`。转换由代码完成，不能手动把两个格式混用。

## 第三阶段：切片推理

在 direct 抽样测试通过后，使用同一测试入口改成：

```powershell
--mode tiled --tile-size 1024 --tile-overlap 0.2 --merge-iou 0.5 --tile-batch 4
```

切片测试重点观察：

- 切片后框是否正确还原到原图坐标。
- 重叠区域是否出现大量重复框。
- 边缘目标是否被截断或漏检。
- 单图最大耗时是否接近或超过 20 秒。
- tiled 与 direct 的检测数量变化是否能通过可视化解释。

## 第四阶段：全量验证

抽样测试通过后，才对固定的 `v1_scene_80_20` 验证集做全量推理和内部指标评估。全量结果必须保留在独立实验输出目录中，不能覆盖 `EXP001` 的训练输出。

全量评估得到的 Recall、FDR 和耗时是内部结果，不是比赛封闭测试成绩。只有比赛评测系统返回的结果才可以作为官方成绩记录。

## 当前边界

- 当前不构建 Docker 镜像。
- 当前不生成 Linux `environment.yml`。
- 当前不上传权重和数据集。
- 当前不使用测试集或官方封闭集反复调阈值。
- 当前 `best.pt` 只是原始标签基线，尚未冻结为最终提交模型。
- 第一轮提交不进行人工审计和标签干预；`AUDIT001` 延后到原始数据官方基线结果之后。
