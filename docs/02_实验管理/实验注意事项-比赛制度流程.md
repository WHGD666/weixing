# 实验注意事项：比赛制度与流程

## 1. 文档定位

本文档只记录比赛制度、流程、提交、测评、晋级和组织管理相关注意事项。

技术路线、数据清洗、模型训练和实验设计放在：

```text
实验注意事项-赛题解决总结.md
```

本文档的作用是防止团队在时间节点、提交材料、测评方式、晋级规则和官方通知上出错。

## 2. 目前已知的比赛阶段

根据赛题文件和答疑，目前比赛大致分为：

| 阶段 | 内容 |
| --- | --- |
| 报名阶段 | 挑战杯系统报名、提交报名材料 |
| 开发阶段 | 获取训练数据，自行划分验证集，开发模型 |
| 测评条件开放 | 官方提供测评条件或测评通道，时间以后续通知为准 |
| 初赛提交/评测 | 提交研究报告、代码、模型和测试结果等 |
| 初审/晋级 | 发榜单位确定入围终审擂台赛的团队 |
| 完善阶段 | 晋级团队根据指导继续完善作品 |
| 终审擂台赛 | 决赛答辩或现场评审，角逐最终奖项 |

原始赛题文件给出的时间安排包括：

- `2026 年 9 月 5 日前`：完成作品提交；
- `2026 年 9 月 20 日前`：完成初审，确定晋级作品和团队；
- `2026 年 10 月`：晋级团队完善作品；
- `2026 年 11 月`：组织终审擂台赛。

答疑中又提到：

- 初赛截止按赛事安排预计在 9 月，具体时间未定；
- `7 月 20 日`不是初赛开始，而是原预计可提供测评条件；
- 测评通道曾通知延期到 8 月下旬；
- 具体测评方式和最终时间以后续官方通知为准。

项目内部建议：

```text
仍按 2026 年 9 月 5 日前完成完整提交材料倒排计划，
但保留根据官方后续通知调整的空间。
```

团队注意事项：

- 不要卡在最后几天等审核；
- 审核未通过时要预留修改时间；
- 所有报名信息应与最终提交信息保持一致。

- 图片编号；

## 4. 测评方式相关

### 4.1 官方测评方式尚未完全固定

答疑中关于测评方式的结论：

- 具体测评方法未定；
- 可能采用网上评测；
- 也可能需要到发榜单位线下评测；
- 是否把代码和权重交给单位统一测，仍以后续通知为准；
- 最终测试环境会统一，但具体硬件尚未完全确定。

原评分方案中的硬件约束：

```text
单张 NVIDIA RTX3090 或同等算力的国产 GPU/NPU
```

团队注意事项：

- 代码不能只在个人电脑路径上运行；
- 环境依赖要写清楚；
- 模型权重、配置、类别映射要完整；
- 推理入口要统一；
- 尽早准备 Docker；
- 不要依赖人工交互。

### 4.2 后续可能要求 Docker 封装

答疑中提到：

```text
到时会请大家利用 Docker 封装，采用同样的接口。
```

这对工程组很重要。

建议提前准备：

- `Dockerfile`；
- 推理入口脚本；
- 模型权重加载路径；
- 输入图像目录；
- 输出结果目录；
- 日志输出；
- 依赖版本；
- GPU 推理支持；
- 无交互运行方式。

推理程序应该满足：

```text
输入图片 -> 自动判断/自动处理 -> 输出检测结果
```

不能要求测试人员告诉程序这是船图、飞机图还是发射车图。

### 4.3 Python、Torch、TensorFlow 版本没有官方固定要求

答疑中明确：

```text
比赛对 python、torch、tf 版本没有要求。
```

但这并不表示可以随意配置。团队仍应固定环境。

建议：

- 固定 Python 版本；
- 固定 PyTorch/CUDA 版本；
- 固定推理框架版本；
- 固定依赖包版本；
- 最终用 `requirements.txt` 或环境说明记录；
- Docker 内环境与本地最终评测环境尽量一致。

## 5. 测试集与反馈信息

### 5.1 官方验证集当前为空，需要自行划分验证集

答疑中说明：

- 下载下来的 `val` 为空是正常的；
- 当前阶段暂不提供测评数据；
- 验证集需要自行划分。

团队注意事项：

- 必须建立自己的训练/验证划分；
- 不要按切片随机划分，避免同一大图泄漏到训练和验证；
- 建议按原始图像或场景划分；
- 本地验证指标要尽量模拟官方口径。

### 5.2 官方反馈暂定到大类指标

答疑中提到，测试得到的反馈数据暂定到大类指标。

也就是说，官方可能只反馈：

- 舰船大类指标；
- 飞机大类指标；
- 发射车/车辆大类指标；
- 总体召回率；
- 总体虚警率；
- 单张大图推理时间。

不一定会反馈 25 个细分类的详细结果。

团队注意事项：

- 本地必须自己输出 25 类详细指标；
- 否则官方反馈不达标时，很难定位哪个类别出了问题；
- 每次提交前都要有本地完整评估表。

## 6. 评分与排名制度

### 6.1 初赛采用刚性指标门槛制

初赛总分 100 分：

| 指标 | 分值 |
| --- | ---: |
| 性能指标基础分 | 70 |
| 方案合理性 | 10 |
| 技术创新程度 | 10 |
| 工程可落地性 | 10 |

必须先通过刚性指标：

| 指标 | 要求 |
| --- | --- |
| 召回率 | `>= 85%` |
| 虚警率/误检率 | `<= 20%` |
| 单幅 `10000 x 10000` 图像推理时间 | `<= 20 秒` |

线上 Docker 测评页面的综合分另有明确的连续计分公式：Recall、False Detection Rate 和 Inference Time 分别按分段函数换算后取平均。该公式与“性能指标基础分 70、方案合理性/创新/工程各 10”的作品总评结构不能混为一谈；项目统一记录在 `shiyan/project_contract/score_contract.md`，并已用官方 `trial-v1.0`、`trial-v2.0` 成绩校验。

答疑中明确：

```text
不达到刚性指标肯定不会进决赛。
```

### 6.2 达标后，性能越好排名越有利

答疑中有人问：

```text
硬性指标达标后，后续评分、排名是否模型性能越好，分数、排名越高？
```

官方答复为：

```text
是的。
```

因此团队不能满足刚性指标后就停止优化。

实际目标应为：

1. 先确保过线；
2. 再尽量提高召回；
3. 同时压低虚警；
4. 控制推理时间；
5. 提升船、飞机、发射车三大类排名。

### 6.3 7 个排名会影响专家打分

评分方案 V1.6 中提到，专家会参考各团队的 7 个排名：

1. 船的召回率排名；
2. 飞机的召回率排名；
3. 车辆的召回率排名；
4. 船的虚警率排名；
5. 飞机的虚警率排名；
6. 车辆的虚警率排名；
7. 总时效性排名。

然后对 7 个排名总和进行二次排序。

这个二次排序会作为以下三项专家打分的重要参考：

- 方案合理性；
- 技术创新程度；
- 工程可落地性。

团队注意事项：

- 不要只优化总体指标；
- 船、飞机、发射车不能有明显短板；
- 时效性也是排名因素；
- 报告中要展示三大类分别的表现。

## 7. 决赛与晋级

### 7.1 晋级原则

根据答疑和评分方案：

- 未达到刚性指标，基本不会进入决赛；
- 进入决赛看排名；
- 达标后性能越好越有利；
- 专家还会看方案、创新和工程落地。

目前材料中没有明确写出固定晋级名额。

项目内部应理解为：

```text
晋级名额以后续官方通知为准。
当前最可靠的策略是先过刚性门槛，再争取三大类指标和时效性排名靠前。
```

### 7.2 决赛类别可能调整

答疑中明确：

- 初赛测试集类别与目前训练集完全一致；
- 决赛可能会有调整；
- 如果决赛新增类别，会提供对应训练集。

团队注意事项：

- 类别配置不要写死到难以扩展；
- 类别映射表要集中管理；
- 模型训练和推理代码应支持后续增加类别；
- 决赛前要关注官方是否补发新类别数据。

### 7.3 决赛评分

决赛总分 100 分：

| 指标 | 分值 |
| --- | ---: |
| 方案合理性 | 20 |
| 技术创新程度 | 50 |
| 工程可落地性 | 30 |

决赛更看重：

- 技术独创性；
- 实际部署潜力；
- 技术路线严谨性；
- 工程稳定性；
- 报告和答辩表达。

因此，初赛阶段就应积累：

- 数据清洗证据；
- 消融实验；
- 错误案例分析；
- 推理速度测试；
- 复现说明；
- 外部数据使用说明；
- 工程封装记录。

## 12. 制度层面结论

制度上最重要的判断是：

1. 初赛先看刚性门槛，不达标基本不能晋级；
2. 达标后性能越好，排名越有利；
3. 7 个排名会影响专家打分；
4. 初赛类别与训练集一致，决赛可能调整；
5. 验证集需要自己划分；
6. 测评方式和环境仍可能变化；
7. Docker 封装要提前准备；
8. 数据问题反馈和修正说明可以成为报告亮点；
9. 晋级名额未明确，奖项名额已有原则性设置；
10. 所有提交材料应按官方后续通知最终校准。
